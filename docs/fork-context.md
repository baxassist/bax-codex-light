# Fork после смены аккаунта: план и границы 0.5.37

## Цель

После смены аккаунта и fork подключать новый точный разговор без копирования ID
пользователем. Не менять родительский разговор, регистрацию, модель и разрешения.
Само создание fork и смену аккаунтов выполняет Codex, не Бакс.

## Выполненная часть

1. Читать `threadId` из метаданных каждого MCP-вызова через официальный SDK.
   `sessionId` не использовать: он может остаться идентификатором корня после fork.
   Метаданные подтверждены source review Codex 0.163.0/0.165.0:
   `core/src/mcp_tool_call.rs`, `with_mcp_tool_call_ids_meta`.
2. Создавать отдельный контекст клиента для вызова; не переписывать ID MCP-процесса.
   Проверять точный thread и cwd через имеющийся AppServer. Параллельные вызовы
   родителя и fork не делят изменяемую привязку. Временный клиент закрывает свои
   фоновые задачи; контроллер проекта продолжает работать.
3. Разрешить `bax_attach()` без аргумента при наличии native-контекста. Если агент
   передал другой ID, отказать до RPC. Некорректные метаданные не превращать в
   fallback на родителя. Для старых клиентов сохранить прежнюю проверку ID процесса.
4. Обновить connect skill: при постоянном разрешении проекта агент выбирает
   текущий fork без дополнительного вопроса пользователю. `bax_status` сам по себе
   не выбирает fork. До первого обращения к MCP переключение не гарантируется.
5. При ошибке восстановления сохранять selected и pending, включая неизвестную
   доставку. Не освобождать writer и не запускать новый разговор вместо отказавшего.

## Проверки

Настоящий STDIO MCP + имитатор AppServer: родитель/fork в одном MCP, параллельные
статусы, отсутствие аргумента attach, сохранённый родительский sessionId,
несовпадение ID для status/attach/resolve/publish, некорректные метаданные,
чужой cwd, active writer и сохранение выбора. Отдельная проверка восстановления
с конфликтом writer сохраняет выбор, неизвестную доставку и доступный фоновой thread.
Это не реальная проверка смены аккаунтов.

## Следующая часть: исполнитель

Метаданные содержат ID, но не подтверждённый endpoint/capability исполнителя.
Текущий контроллер по-прежнему привязан к проекту и регистрации. Поддержка разных
backend одного проекта и надёжная передача endpoint остаются отдельной задачей.
Не считать существование разговора в истории доказательством владения исполнителем.
Standalone CLI с in-process backend без endpoint не становится доступным от этой правки.

Для терминального варианта: отдельно спроектировать управляемый запуск с общим
AppServer и автоматическим `--remote`, без ручного флага в повседневной работе.
Проверить вариант штатного daemon, но не полагаться на незаметный embedded fallback.
Для Desktop нужен подтверждённый канал его backend. Нельзя менять работающий
Codex, вход или настройки ради проверки этой версии плагина.

## Реальная приёмка (ещё не выполнена)

Выделенная машина/профиль, два тестовых аккаунта, два терминала. Зафиксировать
версии Codex, MCP и контроллера, идентичность backend без секретов.

1. A: открыть тестовый разговор, подключить Бакс, завершить контрольную задачу.
2. Штатно сменить вход на B и сделать fork; при первой работе в fork агент
   вызывает status/attach без ID. Подтвердить caller=selected=новый thread.
3. Отправить задачу из Бакса; проверить единственное выполнение в fork под B.
4. Повторить B→A→fork; проверить родительский разговор и второй терминал.
5. Повторить с busy/idle и обрывом после отправки до квитанции: без дублей.
6. Отдельно проверить shared backend и standalone: последний должен отказать
   без попыток обхода writer, завершения процессов или удаления locks.

Очереди старого разговора автоматически в fork не копируются. Новые задачи fork
получают аккаунт при приёме; перенос старых задач и политика продолжения после
смены аккаунта без fork не входят в эту доработку.

## Результаты 02.11.2026

Финальный полный прогон через штатный `unittest.sh --plugin codex-light` с
отдельно подготовленным `BAX_TEST_PLUGIN_RUNTIME`: **373 passed, 11 skipped**,
182,16 с. Ruff check/format, locked sync и diff check прошли. Пропуски относятся
к платформенным/версионным условиям существующих тестов; A→B→fork реально не запускался.

Сохранены исходные отказы: первый полный прогон — 370 passed/13 skipped/1 fail
(ожидание обновления за 0,8 с включало холодный импорт, около 1,5 с на этой машине;
тот же отказ воспроизведён на неизменённой 0.5.36). Тест теперь отдельно проверяет
начало реакции за прежние 0,8 с и завершение настоящего import/update.
Второй полный прогон с упаковкой — 372 passed/11 skipped/1 fail: проверка
восстановления не учитывала EOF WebSocket при намеренном shutdown. Добавлен этот
ожидаемый транспортный отказ в цикл ожидания; прежний срок восстановления 4 с
и проверка нового PID/сохранённого выбора остаются обязательными.

Рабочие аккаунты, регистрации, настройки и установленные процессы не менялись.
Установка/горячая перезагрузка в пользовательском Codex и реальная приёмка остаются
отдельными шагами; этот результат подтверждает исходники и изолированные тесты.
