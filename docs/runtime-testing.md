# Python-окружение плагина и проверка изменений

## Загрузка

`bootstrap.py` требует Python3.11+ и создаёт отдельное окружение. Пользовательские
регистрации и глобальные пакеты не меняются. По умолчанию данные окружения находятся
в `~/.bax/codex-runtime`; `BAX_CODEX_PLUGIN_DATA` переопределяет только этот каталог.

Ключ окружения включает Python cache tag, платформу, первые16 символов SHA-256
`requirements.txt` и ревизию `venv2`. На POSIX используется `venv` с символьными
ссылками на интерпретатор; это сохраняет рабочее разрешение libpython на macOS.
Старые окружения без суффикса не используются и не удаляются, включая частичные.
Обновление базового Python всё равно может потребовать нового исправного окружения:
маркер готовности не является проверкой здоровья всей системы.

Установка использует закреплённые хеши requirements и binary wheels. `.ready`
записывается только после успешной установки. При повторном запуске проверяются
наличие Python и значение маркера; symlink-маркер и чужой digest отклоняются.
Корневой каталог окружения и сам каталог runtime также не могут быть symlink.

`--prepare` создаёт окружение и выдаёт JSON с `ready`/путём Python; MCP и контроллер
этой командой не запускаются. Подготовка скачивает зависимости, тесты сами их не качают.

## Воспроизводимый запуск

```sh
uv sync --locked
.venv/bin/ruff check plugins tests
.venv/bin/ruff format --check plugins tests
export PATH="$PWD/.venv/bin:$PATH"  # python3 у MCP и Python тестов должны совпадать
TEST_ROOT=$(mktemp -d /private/tmp/bax-plugin-check.XXXXXX)
BAX_CODEX_PLUGIN_DATA="$TEST_ROOT/runtime" .venv/bin/python plugins/bax-codex/bootstrap.py --prepare
BAX_TEST_PLUGIN_RUNTIME="$TEST_ROOT/runtime" .venv/bin/pytest tests -q \
  --basetemp "$TEST_ROOT/pytest" --junitxml "$TEST_ROOT/results.xml"
```

Для macOS используйте канонический `/private/tmp`, не symlink `/tmp`, когда путь
передаётся supervisor. Каждому независимому запуску нужен новый каталог. Результаты
и исходные ошибки сохраняйте; общий сброс процессов/пользовательских кэшей не нужен.

Native session и wire-schema тесты закреплены на Codex CLI0.160.0 в PATH. Другая
версия приводит к явному skip; это не PASS и не доказательство совместимости с ней.
Можно указать отдельный тестовый CLI через PATH, не заменяя пользовательский.
Нативные проверки используют собственный CODEX_HOME, временные регистрации и
локальный HTTP-имитатор. Настоящая генерация модели, ключи и разговоры пользователя
не требуются. Проверка установки использует CLI и может обращаться к его каталогу
плагинов; это отличается от платного запроса модели.

## Что доказывают проверки

- `test_bootstrap_runtime.py`: настоящие EnvBuilder/ensurepip и запуск Python/pip;
  только установка зависимостей подменена. Проверяются повторное использование,
  сохранность legacy окружений, отсутствие ready после ошибки и отказ неверного маркера.
- Настоящий `--prepare`: отдельно проверяет установку закреплённых зависимостей.
- `test_plugin.py`: установка в изолированный Codex, сохранение чужих тестовых настроек,
  наличие MCP-инструментов при задержанном старте. HTTP-ответ модели синтетический.
- `test_native_sessions.py`: пустые native-сессии, выбор, reconnect, archive и история;
  это не проверка production-доставки задачи или смены реального аккаунта.

Native-тесты добавляют в JUnit свойства `owned_native_birth`, `owned_native_cleanup`,
`owned_native_catalog_birth`, `owned_native_catalog_cleanup`. Они связывают процессы
с их созданием и фиксируют завершение. При UNKNOWN cleanup набор останавливается.
Supervisor каталога сохраняет исходный exit code CLI отдельно от своего завершения.
Проверка отсутствия собственной группы не доказывает отсутствие потомков, которые
самостоятельно создали новую сессию; эта граница прямо указана в квитанции.

Отчёт об исполнении должен отдельно указывать CLI/Python, PASS/FAIL/skip, результаты
prepare и cleanup. Успешные unit-тесты не заменяют проверку установленного MCP и
занятого контроллера после обновления. Обновление регистрации не требуется.

## Ограничение холодной установки

В проверке04.11 на macOS загрузка wheel `openai-codex-cli-bin` (около122MB)
не уложилась в существующий тайм-аут180с. `.ready` не создан; это сохранённый
отрицательный результат холодной подготовки, а не успешная установка.
Для функциональных проверок те же requirements были установлены в собственный
тестовый runtime через `uv pip install --offline --require-hashes --only-binary :all:`
из уже имеющегося кэша; затем штатный `--prepare` и reuse прошли. Это не доказывает,
что новая загрузка на медленной сети завершится за180с; лимит автоматически не повышался.

Подготавливать runtime нужно тем Python, который запускает MCP. Если pytest
использует3.13, а команда `python3` в PATH указывает на3.14, будут два разных
окружения. В примере PATH явно включает `.venv/bin`; для независимого CLI закрепите
его каталог в PATH, сохраняя этот выбор Python. Не копировать ready между окружениями.

## Результат 04.11.2026 для 0.5.38

На macOS с Python 3.13.13 и отдельным Codex CLI 0.160.0 полный набор:
**389 passed, 0 skipped, 0 failed за 59,42 с**. `uv sync --locked`, Ruff lint
и проверка форматирования также прошли. Обе native cleanup-квитанции подтверждают
отсутствие созданных групп процессов. В тесте каталога исходный CLI завершился с1:
локальный HTTP-имитатор намеренно отвечает400 после получения каталога инструментов;
это не успешная генерация ответа. Завершение supervisor сохранено отдельно.

Исходная попытка с разными Python дала64 PASS и1 FAIL на180-секундной установке
второго runtime. Исправлен выбор PATH для запуска, продуктовый тайм-аут не изменён.
Полный PASS относится к подготовленным зависимостям и изолированному тестовому
Codex; холодная загрузка и обновление занятого пользовательского контроллера
этим результатом не подтверждаются.

## Отложенное обновление общего MCP: 0.5.39

Регрессия `test_shared_caller_updates_after_call_finishes_without_another_tool`
на коде0.5.38 дала настоящий FAIL: контроллер не сменился за10с после idle.
Причина: временный клиент вызова не запускал постоянный discovery и закрывался
в конце вызова. Теперь проверенные клиенты разделены по project/thread и живут
до закрытия MCP; наблюдение продолжает работать между вызовами.

На0.5.39:21/21 проверка контроллера/fork, затем полный набор **390 PASS, без skip,
57,99с**, Python3.13.13/CLI0.160.0. Регрессия использует настоящий локальный контроллер
и AppServer-имитатор; подменяется только версия прежнего PID в ответе status.
Проверяются сохранение busy-процесса, смена PID после idle, прежний выбранный thread
и отсутствие thread/start. Это не readback обновления занятого production-контроллера.
